
# API Versioning

# ADR-006: Adopt URI-Based API Versioning

- **Status:** Accepted
- **Date:** 2026-08-02
- **Decision Makers:** ShopSphere Development Team

## Context

ShopSphere exposes REST APIs that will be consumed by frontend applications and potentially other clients. As the project evolves, APIs may require changes that are not backward compatible.

A versioning strategy is required to allow the application to introduce new API versions while maintaining support for existing clients.

The selected approach should be simple, explicit, and widely adopted within REST-based applications.

## Decision

ShopSphere will use **URI-based API versioning**.

All public REST endpoints will be prefixed with the API version.

Examples:

- `/api/v1/auth/login`
- `/api/v1/products`
- `/api/v1/orders`

Future breaking changes will be introduced through a new version (for example, `/api/v2`) while preserving previous versions until they are deprecated.

## Alternatives Considered

### Header-Based Versioning

Clients specify the API version using custom HTTP headers.

**Reason not selected**

Although it keeps URIs unchanged, it is less visible, harder to test manually, and less intuitive for developers and API consumers.

### Media Type Versioning

API versions are specified using the `Accept` header.

**Reason not selected**

This approach adds complexity without significant benefits for the current scope of ShopSphere.

### No Versioning

Expose endpoints without an explicit version.

**Reason not selected**

Breaking API changes would directly impact existing clients and make long-term API maintenance more difficult.

## Consequences

### Positive

- Provides a clear and explicit API contract.
- Simplifies API evolution and maintenance.
- Allows multiple API versions to coexist during migration.
- Easy to document and test using tools such as Swagger/OpenAPI.
- Aligns with common REST API design practices.

### Trade-offs

- API version becomes part of every endpoint URI.
- Multiple API versions may need to be maintained simultaneously during transition periods.
- Requires a clear deprecation strategy for older API versions.
