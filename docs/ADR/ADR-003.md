
# Package by Feature

# ADR-003: Organize the Codebase Using Package-by-Feature

- **Status:** Accepted
- **Date:** 2026-08-02
- **Decision Makers:** ShopSphere Development Team

## Context

ShopSphere is being developed as a modular monolith with clearly defined business domains and a long-term goal of evolving into a microservices architecture.

As the application grows, organizing source code solely by technical layers (such as controllers, services, and repositories) can make navigation more difficult and increase coupling between unrelated business features.

The project requires a package structure that keeps each business capability self-contained, improves maintainability, and supports future module extraction.

## Decision

The ShopSphere codebase will follow a **Package-by-Feature** organization.

Each business module will contain all components required to implement that feature, including its controllers, services, repositories, entities, DTOs, mappers, exceptions, validators, and other supporting classes.

Example modules include:

- Authentication
- Product
- Inventory
- Cart
- Order
- Payment
- Review
- Notification
- Analytics

Each module owns its implementation while collaborating with other modules through well-defined service boundaries.

## Alternatives Considered

### Package-by-Layer

A structure where all controllers, services, repositories, and entities are grouped into separate top-level packages.

**Reason not selected**

As the application grows, classes related to the same business feature become scattered across multiple packages. This makes feature development, maintenance, and navigation more difficult while increasing coupling between unrelated modules.

## Consequences

### Positive

- Improves code organization around business capabilities.
- Keeps related classes together within the same module.
- Simplifies onboarding and project navigation.
- Reduces coupling between business features.
- Supports independent module development.
- Provides a clear path for extracting modules into microservices in future phases.

### Trade-offs

- Common utilities and shared components require careful organization to avoid duplication.
- Developers must maintain clear module boundaries and avoid introducing unnecessary cross-module dependencies.
