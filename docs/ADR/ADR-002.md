
# Use Modular Monolith

# ADR-002: Adopt a Modular Monolith Architecture

- **Status:** Accepted
- **Date:** 2026-08-02
- **Decision Makers:** ShopSphere Development Team

## Context

ShopSphere is an enterprise e-commerce backend intended to evolve over multiple development phases. The project aims to demonstrate clean architecture, maintainability, scalability, and professional software engineering practices.

Although the long-term vision is to migrate to a microservices architecture, introducing distributed services at the beginning would increase development complexity and slow the learning process. The initial implementation requires a structure that supports rapid development while preserving clear boundaries between business domains.

## Decision

ShopSphere will be developed as a **Modular Monolith**.

The application will be deployed as a single Spring Boot application while organizing the codebase into independent business modules such as Authentication, Product, Inventory, Cart, Order, Payment, Review, Notification, and Analytics.

Each module will encapsulate its own controllers, services, repositories, entities, DTOs, mappers, exceptions, and validators. Communication between modules will occur through well-defined service interfaces within the same application.

The architecture will be designed so that individual modules can be extracted into independent microservices in future phases with minimal refactoring.

## Alternatives Considered

### Traditional Monolith

A single application with modules organized primarily by technical layers.

**Reason not selected**

As the project grows, package-by-layer structures become difficult to navigate and maintain. They also create tighter coupling between unrelated business features, making future service extraction more challenging.

### Microservices from the Beginning

Independent services for each business domain.

**Reason not selected**

Starting with microservices introduces additional operational complexity, including distributed communication, service discovery, centralized configuration, API gateways, observability, and deployment management. These concerns are unnecessary during the early stages of development and would distract from establishing a strong domain model and business logic.

## Consequences

### Positive

- Clear separation of business domains.
- Improved maintainability through package-by-feature organization.
- Simpler local development and deployment.
- Reduced operational complexity during early development.
- Easier testing and debugging compared to distributed systems.
- Smooth migration path toward microservices as the project evolves.

### Trade-offs

- All modules share the same application process and database.
- Module boundaries rely on disciplined code organization rather than deployment isolation.
- Independent scaling of individual modules is not possible until migration to microservices.
